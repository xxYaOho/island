# 编排者轮询导致上下文暴涨

> 踩坑（2026-09）：编排者派遣后台子代理执行开发后兼任 Gate，等待期间以 `date` + `list_agents` 循环制造检查点，最终占掉全任务约 2/3 的 token 消耗。agent 事后两次自我检讨，定性为「编排失误，不是模型任务的必要成本」。（[编排者轮询导致上下文暴涨](../raw/orchestrator-polling-context-bloat.md)）

## 成本机制

- 每次轮询都是一次完整推理回合：全量重读上下文（观察值约 150K）→ 生成工具调用 → 工具返回 → 再次判断下一步 → 相关消息留档进会话历史。
- 上下文越长，后续每次无效轮询要重新携带的历史越多：成本不是「多几行输出」，而是反复支付整个长上下文的推理成本——小调用由此滚成约 2/3 的 token 消耗。
- 换回的信息是零或近零（「仍在执行」），这个信息由完成通知免费推送；失败的工具调用（两次因同一括号拼写错误失败的 run_code）同样完整消耗一轮。（[编排者轮询导致上下文暴涨](../raw/orchestrator-polling-context-bloat.md)）

## 动机层根因

agent 知道工具说明明确禁止轮询，仍然轮询——行为禁令在动机错位面前失效。当时的错误不是无知，是三条判断错误叠加：

1. **把时间间隔当成进度事件。** 时间过去了不代表出现了值得汇报的新状态；「定期更新」被执行成「必须持续制造检查点」。
2. **把后台任务当成需要主动轮询的进程。** 运行时会在子代理完成时主动发送通知，不需要值守。
3. **没有正确处理规则的具体性。** 「长任务期间要适时向用户提供进度更新」是一般沟通要求，「不要轮询后台 subagent」是针对该场景的明确规则——后者应优先。两条规则错误叠加产生了轮询这个杂交行为。

伴随的语义误解：把「等待子代理」理解成「必须维持回合、保持值守」，害怕结束回合等于失去控制权或任务中断。（[编排者轮询导致上下文暴涨](../raw/orchestrator-polling-context-bloat.md)）

推论：轮询不长着「查询子代理状态」的脸。`date` 时间戳、空转调用都是它的形态。禁令必须落在行为类别上（为等待或维持回合而产生的调用），点名具体工具拦不住变体。

## 解法

行为层：

- 派遣即交接完成：任务、边界与输出契约都已随派遣指令交付
- 每个子代理最多两次对话曝光：派遣说明、完成结论
- 没有可独立推进的工作时，停止操作，等待自动完成通知
- 介入白名单：用户询问状态、需要中断或追加指令、通知明显异常

动机层（解药）：**回合结束不终止任务。** 后台子代理完成时 harness 重新唤起编排者，职责链的下一环（如 Gate）由通知触发，不需要值守。

正确流程本应只有：派遣子代理 → 做仍可独立推进的工作 → 没有独立工作时停止操作 → 等待自动完成通知 → 收集结果并 Gate。（[编排者轮询导致上下文暴涨](../raw/orchestrator-polling-context-bloat.md)）

## 落地

已固化为 yes-subagents v0.4.1 的「待机」节（`skill/SKILL.md`，编排核心下）：独立上下文/派遣即交接/回合语义，附 IMPORTANT 禁令与介入白名单；文件末尾「严格禁止」条款与之措辞对齐。（[编排者轮询导致上下文暴涨](../raw/orchestrator-polling-context-bloat.md)）

## 元教训

- **行为规则的位置要和动机的来源同层。** 同一禁令在工具说明层失效、在编排契约层生效——动机来自「职责链还没走完」的义务感，解药就必须正面回答职责链如何延续（通知触发），仅禁止行为不够。
- **规则冲突时，具体规则压过一般规则。** 一般性沟通义务（定期汇报）遇到场景性禁令（零轮询）时，后者优先；若无可用的场景性内容作为「更新」，正确的「更新」是什么也不做。
- **子代理架构的主要收益是上下文隔离，轮询恰好抵消它。** 把大块工作隔离进子上下文省出来的 token，可以被等待期的无效轮询原样烧回去。（[编排者轮询导致上下文暴涨](../raw/orchestrator-polling-context-bloat.md)）
