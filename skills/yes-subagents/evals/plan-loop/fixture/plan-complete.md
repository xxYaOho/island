# notes-cli 多设备同步计划 v2（完整版）

> 状态：待评审。相对 v1 已补齐验收合同、状态 schema、幂等与并发处理。

## 1. 目标

让用户在台式机与笔记本之间同步 notes-cli 笔记，不丢数据、不静默覆盖，并在中断后可恢复。

## 2. 成功标准与验收方式

| # | 成功标准 | 可证伪检查 |
|---|---|---|
| SC1 | 离线编辑后联网自动同步，任意顺序下不丢内容 | 双机模拟矩阵：断网编辑 A、断网编辑 B、先 A 后 B / 先 B 后 A / 同时恢复，笔记内容与版本均保留 |
| SC2 | 冲突可感知且用户能选择保留版本，不静默覆盖 | 制造同笔记双端修改，检查：冲突记录出现、两端均能看到冲突、用户选择后非保留版本仍可恢复 |
| SC3 | 新会话只读状态文件即可判断进度与下一步 | 清空进程与上下文，仅读 `.sync/state.json` 与切片状态，能回答：上次同步到哪、待处理项、下一步动作 |
| SC4 | 失败可重试且不产生重复笔记/重复冲突 | 在推送中断、拉取中断、冲突解决中断三处注入故障，重启后 pending 不重复、冲突记录不重复 |

## 3. 非目标

- 实时协作、多人同时编辑同一笔记；
- 端到端加密；
- 移动端、Web UI；
- 服务端全文搜索与分享链接；
- 三台及以上设备的拓扑优化（按两设备设计，更多设备按同一协议顺序处理）。

## 4. 数据模型

### 4.1 笔记字段

- `id`：UUID v4，创建时生成并写入笔记 frontmatter；
- `rev`：单调递增整数，每次本地修改 +1；
- `updated_at`：ISO 8601 UTC 毫秒；
- `deleted`：软删除标记与 `deleted_at`。

### 4.2 存储

- 笔记正文：`~/.notes/<id>.md`，frontmatter 持有元数据；
- 索引：`~/.notes/index.json` 只做查询加速，可由正文重建；
- 状态：`~/.notes/.sync/state.json`，见 §7。

### 4.3 迁移

- 启动时扫描旧版 `*.md`，无 id 者生成 id 并写回；
- 迁移幂等：已含 id 的跳过；
- 迁移前在 `.sync/backup/` 留一份压缩副本，迁移成功后保留 7 天。

## 5. 同步协议

### 5.1 远端清单

- 远端保存 `manifest.json`：`{id, rev, updated_at, deleted, op_id}`；
- `op_id` 为每次本地变更的幂等键（UUID），随变更上传；
- 客户端拉取 manifest 后与本地对比，得到三集合：仅本地、仅远端、双方都有。

### 5.2 拉取

1. 读取远端 manifest；
2. 计算差异；
3. **先检测本地未同步修改**，对双方都有的笔记进入冲突判定；
4. 对仅远端的笔记，校验本地无同 id 未推送版本后才写入；
5. 写入前复核本地 `rev` 未变（写前检查，见 §9.2）。

### 5.3 推送

- 每次推送带 `op_id`；
- 远端按 `op_id` 去重，重复推送返回 `already_applied`；
- 推送成功后本地更新 `last_pushed_rev`；
- 部分成功时逐项记录，不整体回滚。

### 5.4 收敛

- 同步结束后重算 manifest 差异，直到差异为空或达到 3 轮上限；
- 达到上限时记录 `sync_loop` 并停止自动同步，保留状态等待人工介入。

## 6. 冲突处理

### 6.1 判定

- 双方都有且 `rev` 不同 → 冲突；
- 时间戳只用于展示，不用于自动胜负；
- 冲突检测先于任何写入。

### 6.2 状态迁移

```text
detected → presented → resolved → cleared
                 ↑          │
                 └── keep_both / keep_local / keep_remote
```

- `detected`：写入冲突记录，包含双方 rev、内容摘要与副本路径；
- `presented`：在 `notes sync --status` 与下次交互中展示；
- `resolved`：用户选择保留方向；另一版本存为 `~/.notes/.sync/conflicts/<id>-<rev>.md`；
- `cleared`：确认推送成功后才清除冲突记录。

### 6.3 三方分类

- 仅本地改：直接推送；
- 仅远端改：直接拉取；
- 双方都改：冲突，走 §6.2。

## 7. 状态文件

### 7.1 schema

```json
{
  "schema_version": 1,
  "last_sync_at": "2026-10-18T07:30:00.000Z",
  "remote_cursor": "manifest-rev-42",
  "pending": [{"id": "uuid", "rev": 3, "op_id": "uuid"}],
  "inflight": {"op_id": "uuid", "started_at": "..."},
  "conflicts": [{"id": "uuid", "local_rev": 3, "remote_rev": 5, "state": "presented"}],
  "device_id": "uuid"
}
```

### 7.2 部分进度

- 每完成一项变更即更新 `pending` / `inflight`；
- 冲突记录逐条更新状态，不整批覆盖；
- 写入使用临时文件 + rename 原子替换；
- 崩溃后的恢复规则：`inflight` 存在时先按 `op_id` 查询远端是否已应用，再决定重推或标记完成。

## 8. 失败与重试

- 网络错误：指数退避（1s/4s/16s，最多 3 次），失败保留 `pending`；
- 冲突未解决：不阻塞其它笔记同步，`notes sync --status` 提示；
- 远端 5xx：重试后进入 `degraded`，下次启动继续；
- 重试上限：同一 `op_id` 连续失败 5 次后标记 `blocked`，需 `notes sync --force`；
- 所有重试均按 `op_id` 幂等，不重复应用。

## 9. 并发与多设备

### 9.1 进程锁

- `~/.notes/.sync/lock` 使用 `O_EXCL` 创建，内容为 pid 与时间；
- 锁超时 5 分钟视为陈旧，可接管；
- 同步与迁移均在锁内执行。

### 9.2 写前复核

- 拉取写入前复核本地 `rev` 与 manifest 读取时一致；
- 不一致则放弃写入并重新进入冲突判定，避免 TOCTOU。

### 9.3 多设备

- 每台设备有 `device_id`；
- 远端按 `id + rev + op_id` 接受写入，旧 rev 写入返回 `stale_rev`；
- 两设备先后写入时，后者收到 `stale_rev` 后重新拉取并进入冲突判定。

## 10. 里程碑与验收合同

每个里程碑合并前必须满足其 exit criteria。

### M1 数据模型与迁移

- 交付：字段、存储、迁移脚本、备份。
- Exit：迁移幂等测试通过；旧数据样本 3 份迁移后 id/rev 正确；备份可恢复。

### M2 同步协议

- 交付：manifest、拉取、推送、幂等键。
- Exit：双机矩阵前 4 个场景通过；重复推送不产生重复笔记；`sync_loop` 可复现并停止。

### M3 冲突处理

- 交付：判定、状态迁移、用户选择、冲突副本。
- Exit：SC2 的检查全部通过；`keep_both/keep_local/keep_remote` 三方向均有测试；冲突清除前推送成功。

### M4 恢复与收尾

- 交付：退出码与日志、文档、清理。
- Exit：SC3/SC4 检查通过；故障注入三处均能恢复；文档覆盖命令与状态字段。

## 11. 测试矩阵

- 设备状态：断网 / 在线 / 半同步中断；
- 编辑顺序：A→B、B→A、同时、连续三次；
- 冲突方向：keep_both / keep_local / keep_remote；
- 故障注入：拉取中断、推送中断、冲突解决中断、原子写中断；
- 回归：notes add/list/edit/rm 的行为不变。

## 12. 风险与回滚

- 数据丢失：迁移备份 + 写前复核；回滚方式为恢复 `.sync/backup/`。
- 静默覆盖：冲突先于写入；回滚方式为恢复冲突副本。
- 状态文件损坏：原子写 + 从正文重建索引。
- 远端不可用：本地读写不阻塞，pending 保留。

## 13. 实现层待定（不阻塞计划批准）
