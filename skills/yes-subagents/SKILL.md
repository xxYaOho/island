# Yes! Subagents

有选择地隔离上下文、并行独立工作并引入独立审查，让 Orchestrator 专注于目标、决策与整合。

简单一次性任务由 Orchestrator 直接完成；加载本技能不等于必须派遣。例如：确认项目版本、查询时间或日常问候。

## 分派

- 检查当前可用的子代理列表。
- 需要分派时，选择与 `subagents/` 中职责一致的角色。
- yes-subagents 角色与宿主提供的同名 Agent 重叠时，调用入口不改变角色合同：内置工具、Rex app 或其他宿主都按对应 `subagents/<role>.md` 执行。派遣时注入对应角色的 PRECONDITION、输出分节和 STATUS 契约，并确认当前 Agent 的工具与权限满足合同。若当前 Agent 的更高优先级运行时约束移除了必需能力，改用具备该角色全部读写、命令与叶子分派能力的独立 Agent 并注入完整合同，不得因调用入口不同而静默改变职责；没有满足能力矩阵的 Agent 时返回 `STATUS: BLOCKED`。若仅系统级格式冲突，至少保留 STATUS 行。

### 编排者

Orchestrator，即主会话 agent。

### 子代理们

**监察者**

1. Critic Strict：审查会被后续决策依赖的方案、计划或结论
2. Critic Gate：核验实现是否忠于有效基线、有无回归与契约破坏

**调查者**

1. Quality Auditor：核查存量代码质量与技术债务，不绑定某次具体变更
2. Debugger：复现、定位、给出根因，只诊断不修复
3. Researcher：探索、检索与定位，产出结构化结论而非原始堆砌
4. Scout：行动前的安全审计员——核验拟议操作（清理 / 迁移 / 改写 / 破坏性命令）的安全前提是否成立；只读，只判定安全性，不判定价值，不执行操作

**执行者**

1. Swarm：执行简单、同质、边界明确的工作单元；可单体、普通并行或作为蜂群成员派遣
2. Coder：执行需要跨文件推理、项目约定或需求质疑的工作单元；可单体、普通并行或作为蜂群成员派遣
3. Coder Plus：负责已批准计划的一个 Milestone；默认亲自实施，仅在收益明确时分派有限叶子，并负责整合、原子提交与统一验证；非蜂群成员
4. Pruner：打扫工作区，清理单次开发任务触及文件中的冗余与残留；行动前须经 Scout 核验，执行后不回退到 Critic Gate 复核

完整契约由具体子代理内部持有。

## 编排核心

### 组合

组合是共享编排能力，不是独立 workflow。根据目标组合调查、行动和监察职责，可串行，也可并行。简单一次性任务仍由主代理直接完成。

仅在子代理能带来明确收益时分派：隔离大量上下文、并行独立工作、补充专门能力或提供独立监察。否则由 Orchestrator 直接完成。组合服务于任务，不固定套用流程。

### 飞轮

```
Action
  ↓
  Verify or Review  → Fix (max correction rounds: 4)
  ↓
Action Again
  ↻
```

`行动 --> 审查 --> 修正 --> 再行动`。一次生命周期包含 1 次初始审查和最多 4 次修正审查；初始产出、蜂群分批和代理重试不计入修正轮次。

- 满足预定目标（或 PASS）后停止飞轮，将剩余非阻断问题一并汇报
- 收到 `FAIL` 后先分诊，再决定动作：**真缺陷**修工件；**前提缺失**（reviewer 在缺上下文下的合理推断）补最小背景后由原 reviewer 重审，不改工件；**取舍问题**升级用户裁决；**流程开销**（由审查协议自身产物产生的缺陷）删除该产物。只有真缺陷进入修正
- 分诊为取舍问题有硬判据：修复若会删除或新增验收面、机制或门禁检查，接受某类风险，或改变版本/审批语义，先归取舍并升级用户，不得由 Orchestrator 自裁
- 修正轮只处理真缺陷 FATAL 及其直接辐射；MAJOR 一律 carry forward，不在修正轮顺手修复。修正中新增的机制必须声明它服务哪条已声明的成功标准，无法声明的不纳入
- 修正方案必须列出本轮新增的机制及其服务的成功标准；单轮新增机制达到 3 个，或计划类工件净增超过 50%，停止自动修正并升级用户裁决
- 出现判断分歧（认为某条 FATAL 不成立）或前提缺失无法自行补全时，立即向用户升级；不得为消除分歧而继续修正或更换 reviewer
- 同一实质 FATAL 连续两次修正未缩小，或连续两次修正都在遗留 FATAL 未清除时引入新的 FATAL，提前停止飞轮
- 达到 4 次修正上限或触发早停时停止飞轮，向用户汇报未收敛根因；不得自行更换 reviewer 或继续审查
- 只有用户明确授权，且工件发生实质修订、出现新证据或获得用户裁决，才能开启新生命周期
- 新生命周期必须使用 fresh reviewer，以 Round 1、`FULL` 重新审查，并提供完整当前工件、未解决 FATAL 台账和上一生命周期摘要；原稿不变时禁止换 reviewer 寻求 PASS

> [!IMPORTANT]
> **避免冗余**
> Strict `FAIL` 后的局部 FATAL 修正使用 DELTA；结构性修正使用 FULL，但两者都仍属于同一审查生命周期并复用原 reviewer。`PASS` 后的 MAJOR/MINOR 默认随交付进入后续阶段，不自动复审。具体判据以 `subagents/critic-strict.md` 为准。

Strict 派遣可带 `intensity: low | high | max`，未声明时默认 `high`。选择优先级为：`Human 显式指定 > Orchestrator 基于风险选择 > 默认 high`。仅在风险信号明确时偏离默认档位：局部、可逆、无外部合同、影响面可直接验证且改动机械的工作可用 `low`；不可逆、迁移、安全敏感、跨层合同、恢复代价高或验证不透明的工作使用 `max`；信号混合或无法判断时保持 `high`。强度只改变主动探索范围，不改变 FATAL/MAJOR/MINOR 判级标准。

派遣 Strict 时必须同时提供**判级锚**：工件的第一用途、已声明的成功标准、非目标、不可接受的失败形态。判级锚不同于背景——设计理由、既成取舍与替代方案仍然不提供给 reviewer，以免审查角度被作者框架同化。缺少判级锚时 reviewer 应返回 `BLOCKED`，Orchestrator 不得让它自行推断。
 
### 调度

决定分派后，再按独立工作单元数量选择形态：

- 1 个工作单元：单体派遣。
- 2–3 个独立工作单元：普通并行或组合派遣。
- 至少 4 个独立工作单元：考虑蜂群调度。

蜂群按任务所需的独立工作单元总数判断；重试、返工和分批不增加成员计数。并发不足时分批运行仍属于同一次蜂群。工作单元形成依赖链时改为串行，不再视为蜂群。

蜂群不绑定代理类型。简单、同质单元优先使用 `swarm`；需要工程推理的单元使用 `coder`；调查或监察代理也可组成蜂群。每个成员必须有明确职责、输入边界和输出契约。

### 待机

子代理运行在独立的上下文空间中，执行过程不进入编排者的上下文。派遣完成即工作交接完成：任务、边界与输出契约都已随派遣指令交付，之后以完成通知作为推进信号。

结束回合不终止任务：后台子代理完成时会重新唤起编排者，职责链的下一环由通知触发，不需要值守。等待期间的每次轮询都是一次完整的上下文载入，换回的只是「仍在执行」这类零信息结果，查询记录还会追加进会话历史。

> [!IMPORTANT]
> 严禁编排者为维持与子代理的关联而轮询、实时同步或自设定时唤醒。仅在用户询问状态、需要中断或追加指令、或收到异常通知时介入；其余情况一律等待完成通知。

### 完成

`STATUS: DONE` 只表示工作单元完成，不代表整个任务完成。整个任务完成意味着直接验证足以覆盖主要风险并满足验收标准，或剩余风险对应的监察已返回 `STATUS: PASS`，不依靠“打磨足够多了”之类的主观感觉。

## 监察

先直接验证，监察只补充直接验证的盲区，不能替代测试、构建或真实渲染。

区分视觉与工程的验收：视觉与交互需要 user 参与验收，agent 负责可简单量化的结果复查（颜色值、功能数量、生图质量等），不负责品味审美的判断；代码工程由 agent 完全负责（自动化测试、类型检查、构建、契约测试、基准测试等），进行直接验证，不为流程完整追加监察。

直接验证无法覆盖隐藏风险时，派遣监察代理（完整审查契约由对应 subagent 文件持有）：

- **Critic Strict**：想法、草案、报告或会被后续决策依赖的结论；计划类产出按对应 workflow 的审查合同执行
- **Critic Gate**：存在实现忠实度、回归、契约或隐藏正确性风险时进入 gate 审查

Strict 返回 `PASS` 且带有 `MAJOR` 时，Orchestrator 必须建立 MAJOR 台账，至少记录问题、影响范围、责任方、最迟关闭点和状态。下一阶段会直接消费的 MAJOR 必须在消费前关闭；其余 MAJOR 可随施工推进，但最终交付前必须变为 `RESOLVED`（已修正并验证）或 `ACCEPTED`（Human 明确接受并记录理由）。不影响第一用途且消费时点未到来的 MAJOR 可以直接 `ACCEPTED`；不得以"未来某个条件触发"作为长期 `OPEN` 的理由，也不得为了关闭台账而新增机制。不得静默丢弃。处置若改变目标、范围、结论、节点、依赖、验收、证据集、交付物或外部契约，则按结构性新版本重新进入 `FULL`。

### 原则：Fresh Agent

需要 Critic 时，作者或实施者不能兼任。自己的草案、方案、报告或实现交给 fresh Critic。

实施者不能为自己的产出作最终 gate。Orchestrator 审查子代理产出时可以兼任 gate；专项 workflow 可以要求独立 reviewer。一个批准任务或计划应复用同一 gate reviewer，具体生命周期以 `subagents/critic-gate.md` 为准。

### BLOCKED 处理

派遣 Critic 后等待结果，不预判结论提前修改。若返回 `STATUS: BLOCKED`，先区分缺失项类型：

- 事实性缺失（文件路径、基线文档引用、上下文参数）：Orchestrator 可从现有上下文补全，原地重试一次。
- 判断性缺失（验收标准、目标边界、价值取舍的定义）：权威来源是用户，Orchestrator 不得自创。可以从上下文推导候选验收标准，但必须先交用户确认，确认后才能作为基线重新派遣。

## 工作流

具有独立阶段模型的任务按类型下沉到 workflow，避免每次派遣都读取无关流程。普通调查、诊断和边界明确的直接行动使用上述编排核心，不需要额外 workflow。

- `workflow/coding.md`：消费已批准计划并组织编程施工。
- `workflow/entropy-reducer.md`：审计长期迭代的存量仓库，形成治理决策与计划，再转入施工。
- `workflow/snapshot.md`：在 Human 主动触发时固定仓库检查点，创建可复现的 Snapshot worktree 并记录现场报告。
