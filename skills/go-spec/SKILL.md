# Go! SPEC

基于当前对话上下文及对代码库的理解撰写方案。本技能是 Work to SPEC 文档推进工作模式的起点。

同一份计划文档随对话**逐步长厚**：有议题先落最小记录并持续更新；明确要计划再补决策与草案；确认通过后再写实施细节。厚度由「当前还缺什么」决定，不为流程完整而升层。

## 快速开始

- 新建：`scripts/create.sh <slug>` → 仅记录层骨架。模板真源：`scripts/SPEC_TEMPLATE.md`。
- 升层：`scripts/promote.sh <plan.md> draft|implement` → 按层追加骨架（只追加、不覆盖；已存在则拒绝）。层片段：`scripts/layers/draft.md`、`scripts/layers/implement.md`。
- 撰写 / 更新：综合上下文填入或随讨论更新当前层；升层时先 promote 再填内容，以保持节名与字段风格一致。
- 分派：仅在已有实施层且需要按节点分派时，使用 `scripts/split.sh`。

当上下文信息不足以继续当前层时，借助技能 `grill-me` 追问用户真实的需求目标；该技能不可用时，直接向用户澄清。

## 流程：生长阶梯

```
对话出现议题 / 讨论点
  ↓
记录层（最小文档，持续更新）── 可在此停住并直接推进
  ↓  〔升层：用户明确给出计划动作许可（如要计划 / 升到草案）〕
决策补全 + 草案设计 → 评审 (human) ↻
  ↓  〔升层：用户明确确认草案通过 / 可以写实施〕
实施计划 → 终审 (human / 评审团，由消费方决定) ↻
  ↓
完全交付（可 split 分派）
```

**升层纪律**：不得为「流程完整」主动升层。升层许可必须指向**计划动作本身**（如「要计划」「升到草案」「草案通过」「可以写实施」「要分派」），不得把形状选型、参数拍板、评审意见或其它内容编辑当作升层许可。无显式升层信号时停在当前层并询问，禁止在仅有内容反馈的同一回合自行升层。形状/契约风险可触发询问，但不构成许可。默认停在够用的最薄层；开写或更新时用一句宣告当前停在哪一层。决定升层后：**先 `promote.sh` 追加该层骨架，再填写内容**——活文档不预留空节，风格由层片段真源保证。

**未到的层整层不出现**（不要空节占位，也不要正文写「略过」冒充走过场）。`split.sh` 对缺失层不产片。

文档头 `state` 承载所处阶段：`记录` / `草案` / `已对齐` / `施工中`。

### 1. 记录层：有议题就落盘，禁止无中生有

从对话与上下文中沉淀已讨论的内容，不捏造事实。探查 repo 了解现状；用词尊重项目的领域词汇与既有 ADR。本层目标是**对齐关键信息并可持续更新**，不是写满决策表。

最小集（按实际有则写、无则省略整节）：

- **Problem Statement**：从用户角度看，面临的问题。
- **Solution**：从用户角度看，当前倾向的解决方向（可极短）。
- **Constraints** / **Out of Scope** / **Further Notes**：有红线、排除项、未决或关键参数时再写。
- **扁平任务**：若已有可推进的具体事项，用 `- [ ]` 挂在 `Further Notes`（或独立小节若项目惯例需要）；不引入 Milestone 闸门。

无受益人维度时不要编造 User Stories；无架构取舍时不要硬写 Implementation Decisions。循环动画一类工作：对齐时长、缓动、触发等关键信息即可停在本层推进，**不需要草案，更不需要实施计划**。

记录层交付：保存文档，宣告停在记录层；不等待评审团，不默认 split。

### 2. 决策补全 + 草案设计（升层后）

仅在升层后撰写。先把决策层补到「可审查的结论面」，再写草案。

#### 2.1 决策层字段（有则写）

- **Problem Statement** / **Solution**：同上，升层后应可审。
- **User Stories**：完整的编号用户故事列表。
  - 每条 = 角色 + 诉求 + 动机三要素，编号清单，每条独立可判否；以文档语言成句（禁止中英夹杂）。英文骨架 `As an <actor>, I want <feature>, so that <benefit>` 仅为三要素结构示意，中文文档写成「作为 <角色>，我希望 <诉求>，以便 <动机>」。
  - 无受益人维度的需求（如纯内部优化）则不编造故事。
- **Constraints**：预先存在且全程有效的红线、既有契约、范式惯例。
- **Implementation Decisions**：已作出的实施决策列表。不要包含具体文件路径或代码——它们很快会过时。内容包含：将要构建或修改的模块、接口；开发人员提供的技术说明；架构决策；模式变更；API 契约；具体交互流程。例外：schema、类型形状、状态机等原型片段比散文更精确地编码决策时，可内联并注明来自原型。
- **Testing Decisions**：何为良好测试的标准（仅检测外部行为，而非实现细节）；哪些模块将接受测试及其现有技术。
- **Out of Scope** / **Further Notes**：同上。

#### 2.2 Draft Plan

需求决策补全后，完成一份大纲式、简练的设计方案。它是解决方案的**形状**：关注重点与框架，适当忽略内部实现细节。

Draft 是决策层与执行层的衔接：把结论转译为结构，在写实施计划之前暴露问题。此时调整是推倒重捏，实施中途调整是改产线模具。

- **结构总览**：模块/组件划分与职责、关键数据流（框图级）。
- **关键契约**：模块间接口签名、核心 schema/类型形状（原型片段注明出处）。
- **文件结构**：创建/修改的文件及其责任（文件级，不带行号——行号是实现预支）。
- **风险与未决**：技术风险、需要 spike/原型验证的点、与决策层的潜在冲突。
- **里程碑草案**（可选）：验证主题级粗分组，不含 Task。
- 不写：Task 分解、依赖边、验收细节、测试命令、实现代码。

Draft 完成即停，交 Human 评审（可配合 `Decision.md` / `Draft.md` 切片），**通过后再升入实施层**。若升层后其实无需形状对齐（纯决策沉淀），可只补决策层、不写 Draft，并在交付时说明；决策已稳且适合沉淀时，可询问是否加载 simple-wiki / yes-swiki 记入 wiki（默认否，用户同意再加载）。

### 3. 实施计划（草案确认通过后）

编写实施执行计划。执行者通常是 fresh-agent：一名熟练的开发者，但几乎不了解我们的工具集或问题领域。记录执行所需的**判据与边界**：修改哪些文件（引用 Draft 的文件结构，不复制）、要构建什么（行为、契约、签名级描述，而非实现代码）、进行哪些测试（完整命令与期望输出）、需要查阅哪些文档与既有模式。

**自足 = 判据完整 + 边界明确 + 上下文指引，不是实现预写。**遵循 DRY、YAGNI 和 TDD 原则，进行原子化、频繁提交。

- **Implement Plan**：实施总览——里程碑清单、验证主题地图、推进顺序。文件结构已住 Draft，此处只引用。
- **Milestone**：里程碑是验证主题的分组，不是任务的数量分组。每组交付一个独立可验证的整体，构成推进闸门：验证未通过，不进入下一里程碑。按序编号 `## Milestone-<n>`，节名必须裸编号（不带名称后缀），名称置于正文首行。字段：验证主题 / 核验基线 / 来源标注。切分由风险性质驱动：新公共契约独立成碑、行为改变独立成碑、同质无风险单元合并、依赖构成阻塞边。
- **Task**：层级为里程碑 → 单元 → 步进（单元内部节奏，如 TDD 红-绿-提交，可选）。文档结构即层级：单元嵌于所属里程碑节内，节末即闸门点。Task 编号局部于所属里程碑（`### Task-1`、`### Task-2`……跨里程碑可重复，稳定即可）。字段：验收标准 / 可动文件范围 / 依赖 / 固有风险；来源标注在名称行。
- **Checklist**：步进与任务用 `- [ ]` checkbox 跟踪。

每个里程碑与单元标注来源：通常为 User Story 编号；无故事需求锚定 Problem/Solution；prefactor 类单元注明理由。执行层不允许出现决策层无源的内容；决策层条目不引用执行层（单向引用）。

### 4. 自检（按当前层）

**各层通用**

- **归属**：每条信息只住一层？决策层无路径/代码？执行层无实现预支？
- **不留空白**：无 TBD/TODO/「适当处理」？（未决应写在风险/Further Notes，而非空话）
- **禁止无中生有**：记录与结论均可回溯到对话或 repo 事实。
- **来源档位**：非纯对话来源须标注档位（如 `对话` / `全局约束` / `我方裁量` / `repo 事实`）——同调混写会使正确主张无法审计。

**记录层**

- 关键信息是否已对齐到可推进？未决是否显式列出？

**决策 + 草案层**（仅当本层已写入）

- **闭环断点**：每条需求有方案承接？未覆盖项已显式声明（Out of Scope / 后续批次）？
- **草案承接**：若有 Draft——决策层每条结论在 Draft 有结构承接？Draft 每个结构选择有来源？

**实施层**（仅当本层已写入）

- **来源**：每个方案与单元有来源？
- **一致性**：签名、命名跨单元一致？里程碑编号连续？
- **里程碑**：每个碑有验证主题与核验基线？切分由风险性质驱动而非数量均匀？

发现问题就地修复。

### 5. 交付（按当前层）

- **记录层**：宣告文档路径与「停在记录层」；可继续讨论更新，或直接推进事务。
- **决策 + 草案层**：交人审；通过前不写实施层。
- **实施层**：终审通过后交付预览，需要分派时再 split：

```
计划已完成并通过评审，已保存至 `docs/island/plans/YYYY-MM-DD-<feature-slug>.md`
```

## 切片物化

- `Decision.md`：文档头与决策层整层，服务审查与认知对齐。
- `Draft.md`：设计形状层（结构、契约、文件结构、风险），服务草案评审。
- `Implement.md`：实施总览节，固定的实施计划总览。
- `Milestone-<n>.md`：里程碑整节，含其下全部 Task，服务按节点分派。

识别依据（脚本适配文档；记录层骨架 `scripts/SPEC_TEMPLATE.md`，升层片段 `scripts/layers/*.md`，形态约定一致）：决策层 = 固定英文节名集合；`## Draft Plan` 为草案层；`## Implement Plan` 为实施总览；`## Milestone-<n>` 为里程碑；`### Task-<n>` 为单元。节名即身份；文档状态由文档头承载，不占用节名。

**真源唯一**：主文档变更后重跑 split 全量覆盖，已消失节的旧片自动移除，无变更报告。片是派生物，不带版本历史，历史在主文档的 git 里。

**分派**：只向执行者交付当前节点所需片的路径，禁止交付整目录；防越界（索要/预读后续节点）由消费方派遣契约承担，不属于本机制。记录层默认不 split；无 Draft/Implement/Milestone 时，split 仅可能产出 Decision（若有决策节）。

## 施工期纪律

决策层与通过评审的 Draft 进入施工即冻结，成为执行层的派生基线。实施期发现的决策或形状变更，以追加注记记录，不改写冻结文本。仍停在记录层、尚未升入草案/实施时，文档可随讨论自由更新，不适用冻结。

## 边界

go-spec 是 Work to SPEC 推进模式的起点：假设存在某种评审轮次，但评审形态（谁审、何时审、如何 gate）由消费方决定，本技能只保证**已写入的层**可独立审查与切片。不预设具体下游编排系统——检验任一设计元素：若某外部系统不存在，它是否仍成立？`grill-me` 与 wiki 技能是可选增强，不是运行依赖。
